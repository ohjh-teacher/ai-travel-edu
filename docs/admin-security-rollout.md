# 후기 관리자 권한 적용

현재 소스는 기존 관리자 비밀번호 입력 화면을 유지하면서 Firebase 이메일·비밀번호 인증과 관리자 UID 확인을 연결한 상태다. 관리자 이메일은 첫 사용 때 입력하고 같은 기기에는 기억해 다음부터 비밀번호만 입력한다. 학생 후기 화면은 로그인 없이 제출만 하며, 사진은 공개 다운로드 주소 대신 Storage 경로를 기록한다. 관리자 화면은 로그인 뒤 모든 과정의 후기와 사진을 읽는다.

## 운영 적용 순서

1. Firebase Authentication에서 이메일·비밀번호 로그인을 켜고 사이트 관리자 계정을 하나 만든다. Firebase 콘솔의 Google 로그인과 이 계정은 별개다. 비밀번호는 소스나 대화에 적지 않는다.
2. 생성한 계정의 UID를 Firebase Authentication 사용자 목록에서 확인한다.
3. 확인한 UID로 Firestore에 `admins/{UID}` 문서를 콘솔 관리자 권한으로 만든다. 예를 들어 `role` 필드를 문자열 `admin`으로 넣는다. 클라이언트 규칙은 이 문서의 생성·수정을 허용하지 않는다.
4. Firestore와 Storage 규칙을 함께 배포한다. Storage 규칙의 Firestore 문서 조회에 필요한 서비스 권한을 Firebase가 요구하면 활성화한다. 2026-10-04 두 규칙을 함께 배포했고 컴파일이 통과했다.
5. 로컬 화면과 운영 저장소를 연결해 로그인하지 않은 후기 조회·삭제 거부, 학생 후기 제출·이미지 업로드, 관리자 기존·새 후기 조회·삭제를 확인한다. 2026-10-04 비로그인 후기 조회는 운영 Firestore에서 HTTP 403으로 거부되는 것을 확인했다. 관리자 화면과 학생 제출은 확인 대기 중이다.
6. 확인 결과를 기록하고 `config/security-rollout.json`의 `status`를 `ready-for-hosting`으로 바꾼 뒤 Hosting을 배포한다. 사용자가 규칙 배포 후 로컬 관리자 대시보드가 열린 것을 확인해 `ready-for-hosting`으로 전환했고 2026-10-05 Hosting을 배포했다. 실제 사이트의 첫 화면과 관리자 경로는 HTTP 200을 확인했다. 실제 사이트에서의 관리자 로그인·후기 제출·삭제 동작 확인은 남았다.

## 기존 자료

기존 후기 문서와 사진은 삭제하거나 이동하지 않는다. 이미 발급된 사진 다운로드 주소는 토큰을 가진 사람이 계속 사용할 수 있을 수 있다. 기존 토큰의 재발급·폐기는 별도 점검이 필요하다. 새 제출물은 다운로드 주소를 기록하지 않는다.

## 현재 검증 한계

Google 로그인 제공업체는 이전 안내에 따라 사용자가 켰지만 현재 사이트 관리자 화면에는 사용하지 않는다. 사용자는 이메일·비밀번호 제공업체, 관리자 계정, `admins/{UID}` 문서를 만들었다고 보고했다. Firestore·Storage 규칙 배포 후 로컬 관리자 대시보드가 열린 것을 사용자가 확인했다. 비로그인 후기 조회는 거부됐다. 실제 사이트의 관리자 로그인·삭제, 학생 제출·이미지 업로드 시험은 남았다.
