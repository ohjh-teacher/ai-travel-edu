# 과정·후기 등록 점검 기준

## 적용 범위

정규과정과 특강의 신규 등록, 회차 추가, 후기 양식 변경에 공통으로 적용한다. 작업을 시작하기 전에 기존 과정 하나와 기존 특강 하나의 실제 저장·조회 흐름을 확인한다. 사용자에게 새 로그인 방식이나 별도 관리자 화면을 제안하기 전에 기존 운영 방식을 먼저 기록한다.

## 변경 전 확인

1. 현재 작업 트리와 기존 지침(`AGENTS.md`, 관련 `SKILL.md`)을 확인하고, 충돌하는 지침이 있으면 구현 전에 정리한다.
2. 정규과정은 최초의 `smart-travel`, 특강은 최초의 `custom-travel`을 기준으로 강의안·후기·관리자 연결을 확인한다. 새 구조가 필요한 이유가 없으면 기준 과정의 방식을 재사용한다.
3. 과정의 고유 ID, 유형, 기관, 제목, 회차, 공개 URL, 후기 사용 여부를 확정한다. 같은 ID가 목록·경로·후기 데이터·관리자 화면에서 동일하게 쓰이는지 확인한다.
4. 기존 과정의 콘텐츠 등록 경로와 빌드 입력(`config/project.manifest.json`, `content/catalog.json`)을 대조한다. 생성된 공개 파일을 직접 고치는 방식은 피한다.
5. 기존 후기의 필드, 저장 컬렉션, 관리자 필터와 표시 방식을 확인한다. 과정별 질문은 명시적으로 정의하고, 공통 저장·조회 로직을 복제하지 않는다.

## 사용자가 강의안 자료를 업로드했을 때

자료 등록은 다음 순서로 진행한다. 같은 입력과 같은 작업을 이유 없이 다시 실행하지 않는다.

1. 업로드 파일의 이름, 형식, 크기, 수정 시각과 가능하면 해시를 기록한다. 같은 파일이 이미 처리되었는지 먼저 확인한다.
2. 파일마다 텍스트 추출·OCR·페이지 렌더링·이미지 분석 중 실제로 필요한 처리만 한 번 수행하고, 추출 결과와 페이지별 요약을 작업 파일로 보관한다. 후속 수정에는 이 결과를 재사용한다.
3. 전체 강의안을 만들기 전에 과정 ID, 대상, 회차, 학습 목표, 원본 자료에서 사용한 범위, 빠진 정보와 확인이 필요한 사항을 짧은 등록 계획으로 정리한다.
4. 기존 과정의 강의안 구조와 스타일을 먼저 확인한다. 새 템플릿이나 새 디자인을 매번 생성하지 않는다.
5. 원본 자료의 일부만 바뀌면 변경된 페이지·회차만 다시 읽고 만든다. 전체 파일 추출, 전 회차 생성, 전 슬라이드 렌더링을 자동으로 반복하지 않는다.
6. AI 이미지 생성, 외부 검색, 고비용 변환은 산출물에 꼭 필요한 경우에만 한다. 이미 제공된 이미지와 검증된 자산을 우선 재사용한다.
7. 빌드와 검증은 필요한 범위부터 실행한다. 오류가 발생한 부분만 수정·재검증하고, 전체 검증은 제출 직전에 한 번 수행한다. 동일한 명령을 근거 없이 반복하지 않는다.
8. 중간 산출물과 실행 결과를 기록해 작업이 중단되어도 완료된 단계부터 이어간다. 사용자에게 같은 자료를 다시 업로드하게 하거나 같은 처리를 다시 청구하지 않는다.

재실행은 입력 파일 변경, 관련 소스 변경, 검증 실패, 누락된 결과처럼 구체적인 이유가 있을 때만 한다. 재실행 전에는 대상·이유·예상 범위를 확인한다. 비용을 줄이기 위해 필수 확인을 생략하거나 실제로 실행하지 않은 검증을 완료로 표시하지 않는다.

### 자료 캐시 사용

로컬 경로가 있는 자료는 처리 전에 다음 명령으로 확인한다. `status: reuse`이면 기록된 결과물을 사용한다. `status: process`이면 필요한 추출만 수행한다.

```text
node tools/material-intake.mjs status <원본파일> --processor pdf-text-v1
```

추출 결과를 출력된 `cacheDirectory` 아래에 저장한 뒤 기록한다.

```text
node tools/material-intake.mjs record <원본파일> --processor pdf-text-v1 --artifact <캐시디렉터리/추출결과.txt>
```

이 도구는 텍스트 추출이나 OCR을 수행하지 않는다. 원본과 결과물의 해시로 이미 수행한 처리를 재사용할 수 있는지만 판정한다. 추출 방식이 달라지면 `--processor`의 버전을 올린다. 페이지별 부분 재처리는 추출 도구가 페이지별 결과물을 만들 때 해당 페이지에 적용한다.

## 구현 경계

- 과정 내용과 질문 문구는 과정별 데이터로 둔다. 저장, 검증, 관리자 조회, 오류 처리는 공통 로직으로 유지한다.
- 후기 레코드에는 안정적인 과정 ID와 질문 버전을 넣는다. 화면 제목이나 URL 문자열로 과정을 추론하지 않는다.
- 새 후기에는 `courseId`(카탈로그 ID), `questionVersion`(정수), 기존 저장 흐름에 필요한 `lectureId`·`lectureTitle`을 함께 기록한다. 문항별 후기는 `questionAnswers: [{ question, answer }]`로 저장하면 공통 관리자 화면에 표시된다. 기존 레코드에 이 필드가 없어도 조회할 수 있어야 한다.
- 후기 입력 항목을 바꾸면 저장 형식뿐 아니라 기존 관리자 화면의 필터·표시·내보내기까지 함께 확인한다.
- 기존 레코드를 읽을 수 있어야 한다. 필드나 질문 형식을 바꿀 때 이전 데이터의 표시 방식을 명시한다.
- 사용자 흐름과 데이터 접근 제어를 분리해 검토한다. 관리자 화면의 비밀번호만으로 저장소 읽기 권한이 제한된다고 가정하지 않는다.
- 새 강의가 생겨도 관리자 화면을 복제하지 않는다. 첫 화면의 관리자 진입점과 공통 후기 목록에서 새 과정의 기록을 조회·삭제할 수 있는지 확인한다. 학생용 QR은 제출 화면으로만 연결한다.
- 모든 과정의 학생용 후기 화면은 강의안·전체 과정·포털과 분리된 독립 페이지로 구성한다. 후기 화면에 전체 강의 사이트로 이동하는 버튼·링크·자동 이동이 없어야 하며, 사용자의 명시적 승인 없이 이를 추가하지 않는다.
- 현재 관리자 인증 전환의 순서는 `docs/admin-security-rollout.md`를 따른다. `config/security-rollout.json`이 `pending`이면 과정별 Hosting 배포를 진행하지 않는다. 전환 완료 후 과정별 게시에는 `firebase deploy --only hosting`을 사용한다.

## 공개 전 확인

| 영역 | 확인할 사항 |
| --- | --- |
| 목록·경로 | 정규/특강 목록, 상세 페이지, 회차, 후기 링크, QR이 실제 공개 URL로 연결되는가 |
| 후기 | 필수 입력, 동의, 중복 제출, 실패·재시도, 제출 완료 안내가 동작하며, 후기 화면에서 강의안·전체 과정·포털로 이동하는 연결이 없는가 |
| 관리자 | 새 과정 필터와 문항별 답변이 기존 관리자 화면에 나타나는가; 이전 후기도 계속 보이는가 |
| 개인정보 | 이름 등 수집 항목의 필요성, 저장소 읽기·수정·삭제 권한, 보존·삭제 방식을 확인했는가 |
| 배포 | 로컬 규칙과 실제 배포 규칙, 사이트 파일과 데이터 저장소 설정을 각각 확인했는가 |
| 품질 | 빌드·검증 명령, 모바일/프로젝터 화면, 키보드 접근, 깨진 링크를 확인했는가 |
| 강의안 처리 | 업로드 파일의 중복 처리, 변경된 회차만 재생성, 기존 이미지 재사용, 불필요한 전체 렌더링을 확인했는가 |

## 현재 확인된 위험과 추가 조사

직전 용산 과정 작업 기록에는 후기 제출이 비활성화되어 있고, 관리자 화면에 용산 질문의 표시 처리가 없다고 기록되어 있다. 같은 기록에서 로컬 `firestore.rules`의 후기 읽기·삭제 허용 범위가 넓다고 확인했다. 실제 배포 규칙은 확인되지 않았다. 이 세 항목은 배포 전에 현재 파일과 배포 환경을 다시 대조해야 한다.

추가로 과정 ID의 단일 관리 여부, 후기 데이터의 질문 버전, 이전 데이터 호환, 개인정보 보존·삭제 절차, 오류 시 재제출 동작, QR의 배포 URL, 목록·상세·후기 사이의 링크 무결성, 생성 파일과 원본 파일의 경계를 점검한다.

## 완료 판정

과정 등록, 후기 제출, 기존 관리자 조회, 접근 권한, 빌드 검증을 한 흐름으로 확인한 뒤 완료로 표시한다. 확인하지 못한 항목은 완료로 간주하지 않고 이유와 영향을 작업 결과에 남긴다.
